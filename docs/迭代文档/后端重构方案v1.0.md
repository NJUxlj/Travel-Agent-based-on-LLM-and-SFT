### 1.2 重构目标

1. **MAS 架构**：建立清晰的多 Agent 协作框架，每个 Agent 内置 MCTS 思考链
2. **训练管线**：统一 CPT → SFT → RL（PPO/DPO/TRPO/GRPO）管线，支持选择性执行
3. **部署闭环**：集成 vLLM 部署管理，Agent 通过 OpenAI-compatible API 调用本地模型
4. **API 化**：所有能力通过 FastAPI HTTP/WebSocket 暴露，前后端彻底解耦
5. **可维护性**：单一职责、依赖注入、统一配置、完整类型标注

## 三、核心架构设计

### 3.1 多智能体系统 (MAS) 架构

#### 3.1.1 Agent 角色定义

```
┌─────────────────────────────────────────────────────────┐
│                    Orchestrator（编排器）                  │
│         任务分解 → Agent 调度 → 结果聚合 → 冲突消解         │
└────┬──────────┬──────────┬──────────┬───────────────────┘
     │          │          │          │
     ▼          ▼          ▼          ▼
┌─────────┐┌─────────┐┌─────────┐┌─────────┐
│ Planner ││  Info   ││ Budget  ││ Critic  │
│  Agent  ││  Agent  ││  Agent  ││  Agent  │
│ 行程规划 ││ 信息搜集 ││ 预算优化 ││ 方案评审 │
└─────────┘└─────────┘└─────────┘└─────────┘
     │          │          │          │
     └──────────┴──────────┴──────────┘
                    │
         ┌─────────┴─────────┐
         │  Qwen3-4B (vLLM)  │
         │  OpenAI-compat API │
         └───────────────────┘
```

| Agent | 职责 | 典型输出 |
|-------|------|---------|
| **Orchestrator** | 接收用户旅行需求，分解为子任务，分配给专业 Agent，聚合结果，处理 Agent 间冲突 | 最终旅行方案 |
| **PlannerAgent** | 根据目的地、天数、偏好生成行程安排（每日路线、时间分配） | 结构化行程 JSON |
| **InfoAgent** | 搜集目的地信息（景点、天气、交通、美食、文化习俗） | 信息摘要 |
| **BudgetAgent** | 估算各项费用，在预算约束下优化方案 | 预算分配表 |
| **CriticAgent** | 评审方案的合理性（时间冲突、路线效率、遗漏项） | 改进建议列表 |

> **约定**：`thinking_process` 中的 `agents_involved` 与 `thinking` 事件中的 `agent` 字段使用小写标识符（`orchestrator`/`planner`/`info`/`budget`/`critic`），便于前后端统一映射。

#### 3.1.2 Agent 协作流程

```
用户输入: "帮我规划一个北京5日游，预算8000元，喜欢历史文化"
    │
    ▼
[Orchestrator] 分解任务
    ├──→ InfoAgent: 搜集北京景点/天气/交通/美食信息
    ├──→ PlannerAgent: 基于信息生成5日行程
    ├──→ BudgetAgent: 在8000元约束下优化
    └──→ CriticAgent: 评审方案
    │
    ▼ (可能多轮迭代)
[Orchestrator] 聚合 → 返回最终方案
```

#### 3.1.3 BaseAgent 核心抽象

每个 Agent 的 `think()` 方法内部运行 MCTS，在每个思考节点自主决策：

```python
class BaseAgent(ABC):
    """所有 Agent 的基类"""

    def __init__(
        self,
        agent_id: str,
        role: str,
        system_prompt: str,
        llm_config: LLMConfig,       # model_name, base_url, api_key
        rag_retriever: BaseRetriever | None = None,
        tools: list[BaseTool] | None = None,
        mcts_config: MCTSConfig | None = None,
    ): ...

    async def think(self, task: str, context: dict) -> AgentResponse:
        """
        使用 MCTS 进行结构化思考。
        在每个思考节点，Agent 自主决策下一步动作。
        """
        mcts = MCTSSearch(config=self.mcts_config)
        root = ThoughtNode(state={"task": task, "context": context})

        for _ in range(mcts.num_simulations):
            # 1. SELECT: PUCT 选择最优思考路径
            leaf = mcts.select(root)

            # 2. EXPAND: LLM 生成候选动作并扩展
            actions = await self._generate_actions(leaf)
            mcts.expand(leaf, actions)

            # 3. EVALUATE: LLM 评估当前思考质量
            value = await self._evaluate(leaf)

            # 4. BACKPROPAGATE: 更新路径价值
            mcts.backpropagate(leaf, value)

        # 选择最优思考链
        best_path = mcts.get_best_path(root)
        return self._compose_response(best_path)

    async def _generate_actions(self, node: ThoughtNode) -> list[Action]:
        """
        根据当前思考状态，生成候选动作。
        动作类型：THINK（继续推理）| USE_RAG（检索）| USE_TOOL（调用工具）| OUTPUT（输出结论）
        由 LLM 自主判断。
        """
        prompt = self._build_action_prompt(node)
        response = await self.llm.chat(prompt)
        return self._parse_actions(response)
```

### 3.2 MCTS 思考引擎

#### 3.2.1 动作空间

```python
class ActionType(str, Enum):
    THINK = "THINK"           # 继续推理（生成下一步思考）
    USE_RAG = "USE_RAG"       # 检索知识库
    USE_TOOL = "USE_TOOL"     # 调用外部工具
    OUTPUT = "OUTPUT"         # 输出最终结论

@dataclass
class Action:
    action_type: ActionType
    content: str              # 思考内容 / RAG query / Tool call / 输出文本
    tool_name: str | None     # USE_TOOL 时的工具名
    tool_args: dict | None    # USE_TOOL 时的工具参数
    prior_prob: float         # LLM 给出的先验概率
```

#### 3.2.2 ThoughtNode 结构

```python
@dataclass
class ThoughtNode:
    state: dict                       # 当前思考状态
    action: Action | None = None      # 到达此节点的动作
    parent: ThoughtNode | None = None
    children: list[ThoughtNode] = field(default_factory=list)
    visits: int = 0
    value_sum: float = 0.0
    prior_prob: float = 1.0

    # RAG / Tool 执行结果（如果此节点执行了 RAG 或 Tool）
    retrieval_result: str | None = None
    tool_result: str | None = None
```

#### 3.2.3 MCTS 搜索流程

```
         [Root: 用户任务]
              │
    ┌─────────┼──────────┐
    ▼         ▼          ▼
[THINK:    [USE_RAG:   [USE_TOOL:
 分析需求]  搜索景点]   查天气]
    │         │          │
    ▼         ▼          ▼
 [THINK:   [THINK:   [THINK:
  细化]    整合信息]   分析天气]
    │         │
    ▼         ▼
[OUTPUT:  [USE_TOOL:
 初步方案]  查酒店]
              │
              ▼
           [OUTPUT:
            完善方案]
```

每一步的决策流程：

```
1. SELECT   → PUCT 公式选最优子节点
2. EXPAND   → 调用 LLM 生成 [THINK, USE_RAG, USE_TOOL, OUTPUT] 候选
3. EVALUATE → LLM 对思考链打分（0-1, 考虑：完整性/准确性/创意性）
4. BACKUP   → 沿路径回传价值
```

#### 3.2.4 RAG / Tool 自主决策机制

在 EXPAND 阶段，LLM 通过如下 prompt 自主判断是否需要 RAG 或 Tool：

```
你正在为旅行规划进行深度思考。当前思考链：
{thought_chain}

当前需要决定下一步动作。可选动作：
1. THINK: 继续推理分析
2. USE_RAG: 从知识库检索信息（当你需要特定目的地/景点/交通信息时）
3. USE_TOOL: 调用外部工具（可用工具：{tool_descriptions}）
4. OUTPUT: 输出当前阶段的结论

请输出你的决策和理由，格式：
ACTION: <动作类型>
REASON: <决策理由>
CONTENT: <具体内容/查询/工具调用>
CONFIDENCE: <0-1 置信度>
```

```python
class LLMConfig:

class LLMClient:
    """OpenAI-compatible 异步客户端，对接 vLLM"""

    def __init__(self, config: LLMConfig):
        self.client = AsyncOpenAI(
            base_url=config.base_url,

        )
        self.model = config.model_name

    async def chat(
        self,
        messages: list[dict],
        temperature: float | None = None,
        max_tokens: int | None = None,
    ) -> str: ...

    async def stream_chat(
        self,
        messages: list[dict],
        **kwargs,
    ) -> AsyncIterator[str]: ...
```

## 五、TravelAgentFinetuneMASPipeline

### 5.1 Pipeline 完整流程

```python
class TravelAgentFinetuneMASPipeline:
    """
    端到端管线：数据加载 → 微调 → vLLM 部署 → MAS 启动

    可通过 HTTP API 触发，支持断点续跑。
    """

    def __init__(self, config: PipelineConfig): ...

    async def run(self, stages: list[str] | None = None) -> PipelineResult:
        """
        执行完整管线或指定阶段。
        stages: ["load_data", "cpt", "sft", "rl", "deploy", "start_mas"]
        """
        result = PipelineResult()

        # Stage 1: 加载数据集
        if "load_data" in stages:
            result.data = await self._load_data()

        # Stage 2: 持续预训练 (CPT)
        if "cpt" in stages:
            result.cpt = await self._run_cpt(result.data)

        # Stage 3: 监督微调 (SFT)
        if "sft" in stages:
            result.sft = await self._run_sft(result.data)

        # Stage 4: 强化学习 (RL) — 支持选择具体方法
        rl_stages = [s for s in stages if s in ("dpo", "ppo", "grpo", "trpo")]
        for rl_stage in rl_stages:
            result.rl = await self._run_rl(result.data, method=rl_stage)

        # Stage 5: 模型评估
        if "evaluate" in stages:
            result.eval = await self._evaluate()

        # Stage 6: vLLM 部署
        if "deploy" in stages:
            result.deployment = await self._deploy_vllm()

        # Stage 7: MAS 启动
        if "start_mas" in stages:
            result.mas = await self._start_mas()

        return result
```

## 十、关于需求中不合理之处的建议

### 10.1 TRPO 在 LLM 对齐中的实用性

**问题**：TRPO 需要对整个策略参数空间计算 Fisher 信息矩阵的逆（共轭梯度），在数十亿参数的 LLM 上**计算成本极高**，且 2024-2026 年主流 RLHF 研究和工程实践几乎已不使用 TRPO。PPO 的 clip 机制已经是 TRPO 的高效近似，GRPO 进一步去掉了 Critic。

**建议**：保留 TRPO 训练器代码作为学术完整性，但在 Pipeline 默认配置和文档中**标注为实验性功能**，推荐用户使用 **DPO + GRPO** 组合（当前最主流且效果好）。

### 10.2 "所有能力都暴露为独立 HTTP 服务"

**问题**：
- vLLM 部署/停止是**服务器生命周期管理**操作，用 HTTP 触发没问题，但需要注意**权限控制**（防止误操作停掉正在服务的模型）
- 训练任务可能运行数小时，不适合同步 HTTP 请求，需要异步任务模式
- MAS 启动本质上是"将 Orchestrator 设为就绪状态"，不需要独立端点，跟随 vLLM 部署状态即可

**建议**：
- 训练/评估/Pipeline：采用 `POST 创建 → 202 Accepted → GET 轮询/WebSocket 推送` 异步模式
- vLLM 部署：增加确认机制，防止误停
- MAS 启动：合并到 Pipeline 或 Deployment 流程中，不单独暴露（因为 MAS 本身是无状态的，只要 vLLM 在运行，任何 `/chat` 请求都会触发 MAS 协作）

### 10.3 四种 RL 方法同时训练

**问题**：在一个 Pipeline 中串行执行 PPO → DPO → TRPO → GRPO 训练**没有意义**——每种方法都是对同一基础模型的不同对齐策略，串行执行意味着后面的方法覆盖前面的效果。

**建议**：Pipeline 支持**选择其中一种**（如 GRPO），而不是全部执行。配置中使用 `rl_method: "grpo"` 让用户选择。如果想比较不同方法，应该创建多个 Pipeline **并行分支训练**后分别评估对比。

### 10.4 Qwen3-4B 的能力边界

**问题**：4B 参数的模型同时承担 MCTS 多步推理 + RAG 判断 + 工具调用判断 + 多 Agent 角色扮演，能力可能吃紧，特别是 MCTS 的每个节点都需要一次 LLM 推理。

**建议**：
- MCTS 模拟次数不宜过大（建议 20-50 次，而非棋类的 800 次）
- 初期可以简化为 **Orchestrator 用更大模型**（如 Qwen3-14B 或 API），专业 Agent 用微调后的 4B 模型
- 或者 MCTS 搜索宽度限制为 3-4（每步最多 3-4 个候选动作）
